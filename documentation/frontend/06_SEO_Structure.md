## 1. Introduction

This document defines the SEO architecture for the Nepack Website. It establishes the planning-level structure for URLs, metadata, headings, structured data, breadcrumbs, product SEO, brand SEO, image SEO, download SEO, internal linking, redirects, pagination, and performance-related SEO considerations.

The document is intended to guide future SEO implementation for public pages and dynamic CMS-managed content.

This document does not include implementation code, HTML, CSS, JavaScript, PHP, database schema, `.htaccess` rules, `robots.txt` content, or XML sitemap files.

---

## 2. SEO Objectives

| Objective | Description |
|---|---|
| Improve Organic Discoverability | Make company, product, brand, and document pages discoverable through search engines. |
| Support Product-Led Search Intent | Optimize product categories, product details, part numbers, and technical product content. |
| Support Local Business Visibility | Strengthen relevance for Guwahati, Assam, Northeast India, and approved service regions. |
| Improve Crawlability | Ensure important public pages are reachable through sitemap, navigation, breadcrumbs, and internal links. |
| Avoid Duplicate Content Issues | Define canonical, pagination, and URL consistency rules. |
| Support CMS SEO Governance | Allow administrators to manage metadata, slugs, image alt text, and page-specific SEO content. |
| Improve Search Result Presentation | Prepare metadata, Open Graph, Twitter Card, and structured data guidelines. |
| Maintain Scalable SEO | Support future product lines, brands, categories, industries, applications, and content sections. |

## 3. SEO Principles

| Principle | Application |
|---|---|
| User Intent First | SEO content should match what engineers, buyers, and procurement users are searching for. |
| Descriptive URLs | URLs should describe the content clearly using lowercase hyphenated slugs. |
| Unique Metadata | Each indexable page should have a unique title and description. |
| Single Primary Topic | Each page should focus on one clear content purpose. |
| Crawlable Hierarchy | Product, brand, download, and gallery pages should be reachable through internal links. |
| Canonical Consistency | Duplicate or alternate URLs should identify a preferred canonical destination. |
| Content Quality | Product and brand pages should contain useful, accurate, and non-thin content. |
| Image Optimization | Images should support both accessibility and search visibility. |
| Technical Cleanliness | Broken links, missing metadata, and orphan pages should be avoided. |
| Future Scalability | SEO rules should support expansion without changing established patterns. |

## 4. Global SEO Strategy

Global SEO applies across all public-facing pages.

| SEO Area | Global Strategy |
|---|---|
| Page Titles | Every public page should have a unique, descriptive title. |
| Meta Descriptions | Each page should include a concise summary aligned to search intent. |
| URL Slugs | Slugs should be readable, lowercase, hyphen-separated, and stable. |
| Headings | Each page should have one clear H1 and logical H2-H6 hierarchy. |
| Internal Links | Important pages should be linked from relevant pages, footer, sitemap, and related-content areas. |
| Breadcrumbs | Inner pages should include breadcrumb structure for usability and SEO. |
| Images | Images should have descriptive filenames and alt text. |
| Indexing | Only valuable public pages should be indexable. Admin, duplicate, error, and low-value system pages should not be indexable. |
| Performance | Pages should be optimized for loading speed, image delivery, layout stability, and mobile usability. |
| CMS Control | Admin users should be able to manage metadata for public pages and dynamic records. |

## 5. URL Structure Guidelines

URLs should be conceptual, SEO-friendly, and aligned with the sitemap.

| Rule | Guideline |
|---|---|
| Lowercase | Use lowercase characters only. |
| Hyphenated Slugs | Separate words with hyphens. |
| No Spaces | Spaces should not appear in URLs. |
| No Special Characters | Avoid unnecessary punctuation, symbols, or encoded characters. |
| Avoid Public IDs | Public URLs should avoid database IDs where practical. |
| Stable Paths | Avoid changing URLs after publication. |
| Descriptive Terms | Use meaningful product, category, brand, and document names. |
| Hierarchy Where Useful | Reflect parent-child relationships for products, categories, downloads, and gallery pages. |

### Conceptual URL Examples

| Page Type | Example |
|---|---|
| Home | `/` |
| About | `/about-us` |
| Products | `/products` |
| Product Line | `/products/smc-product-line` |
| Product Category | `/products/smc-product-line/pneumatics` |
| Product Detail | `/products/smc-product-line/pneumatics/one-touch-fittings-kq2-series` |
| Brand Detail | `/brands/smc` |
| Download Category | `/downloads/datasheets` |
| Download Detail | `/downloads/datasheets/kq2-series-datasheet` |
| Gallery Category | `/gallery/product-gallery` |
| Gallery Detail | `/gallery/product-gallery/pneumatic-fitting-display` |
| Contact | `/contact-us` |

| Rule | Description |
|---|---|
| Must be unique | Each indexable page should have a distinct description. |

| Should be concise | Keep descriptions short enough for search result usability. |

## 8. Heading Structure Guidelines H1-H6

Heading structure should support content clarity and search engine understanding.

| Heading Level | Usage Guideline |
|---|---|
| H1 | One primary page topic only. |
| H2 | Major content sections on the page. |
| H3 | Subsections under H2 sections. |
| H4 | Supporting groups, tables, or nested content where needed. |
| H5 | Rarely used; only for deep structured content. |
| H6 | Avoid unless necessary for complex documentation-style pages. |

### Page-Level Heading Examples

| Page Type | Recommended H1 |
|---|---|
| Home | Nepack or Industrial Automation Products and Solutions |
| About | About Nepack |
| Products Landing | Products |
| Product Category | `{Category Name}` |
| Product Detail | `{Product Name}` |
| Brands Landing | Brands |
| Brand Detail | `{Brand Name}` |
| Downloads | Downloads |
| Gallery | Gallery |
| Contact | Contact Us |
| Search Results | Search Results |

### Heading Rules

| Rule | Description |
|---|---|
| Use one H1 per page | Avoid multiple competing primary headings. |
| Do not skip hierarchy unnecessarily | Maintain logical order from H1 to H2 to H3. |
| Match content purpose | Headings should describe the content below them. |
| Avoid decorative headings | Headings should not exist only for visual styling. |
| Support dynamic pages | Product, brand, category, and download pages should generate meaningful headings from content names. |

## 9. Canonical URL Strategy

Canonical URLs should identify the preferred version of a page where duplicate or alternate paths may exist.

| Scenario | Canonical Recommendation |
|---|---|
| Product reachable through category and brand | Product detail canonical should point to the primary product detail URL. |
| Filtered product listings | Canonical should point to the main category/listing page unless filtered page is intentionally indexable. |
| Search results | Search result pages should generally not be treated as primary indexable pages. |
| Pagination | Paginated pages should maintain clear self-reference or parent strategy based on final SEO decision. |
| Download documents linked from product and download library | Download detail canonical should point to the primary document detail URL. |
| HTTP/HTTPS or trailing slash variants | Canonical should use one preferred site-wide URL format. |
| Duplicate slugs | Duplicate slug creation should be prevented conceptually. |

### Canonical Rules

| Rule | Description |
|---|---|
| Every indexable page should have a canonical reference | Helps reduce duplicate content ambiguity. |
| Canonical should match preferred public URL | Avoid pointing to redirected or non-preferred paths. |
| Dynamic content should generate stable canonical URLs | Products, brands, downloads, and gallery pages require consistent canonical handling. |

## 12. XML Sitemap Strategy

The XML sitemap should help search engines discover public indexable URLs.

| Sitemap Area | Include |
|---|---|
| Static Pages | Home, About, Contact, Privacy Policy, Terms & Conditions, Sitemap. |
| Products | Product landing, product lines, categories, subcategories, product details. |
| Brands | Brand landing and active brand detail pages. |
| Downloads | Download landing, document categories, document detail pages where indexable. |
| Gallery | Gallery landing, gallery categories, gallery details where indexable. |
| Future Pages | Applications, industries, case studies, services, blog pages when added. |

### XML Sitemap Rules

| Rule | Description |
|---|---|
| Include only public indexable pages | Admin, search results, 404, drafts, archived items, and private files should be excluded. |
| Reflect publish status | Only active CMS content should appear. |
| Update with content changes | Sitemap should account for newly published or archived dynamic content. |
| Use canonical URLs | Sitemap URLs should match canonical public URLs. |
| Avoid duplicate URLs | Each page should appear once in the sitemap. |

## 13. robots.txt Strategy

The robots strategy should guide crawler access without exposing sensitive details or relying on robots rules for security.

| Area | Recommendation |
|---|---|
| Public Pages | Allow crawl access for indexable pages. |
| Admin Area | Prevent indexing and crawling of administrative paths. |
| Search Results | Prevent indexing if search result pages are not intended as SEO landing pages. |
| Duplicate / Filtered URLs | Prevent or canonicalize where needed based on SEO strategy. |
| Media Files | Allow crawl access to public images and PDFs that should appear in search. |
| Private Uploads | Do not expose private or unpublished files publicly. |
| XML Sitemap Reference | Provide sitemap discovery conceptually. |

### robots.txt Rules

| Rule | Description |
|---|---|
| Not a security control | Sensitive pages must be protected by authentication, not only crawler rules. |
| Avoid blocking important assets | Public CSS, JS, images, and useful PDFs should not be blocked if needed for indexing. |
| Keep rules simple | Avoid complex crawler directives unless necessary. |
| Align with sitemap | Crawl allowances should not conflict with sitemap inclusion decisions. |

## 22. Redirect Strategy

Redirect planning should preserve SEO value and user experience when URLs change.

| Scenario | Redirect Recommendation |
|---|---|
| Changed Product URL | Redirect old product URL to new product URL. |
| Archived Product | Redirect to parent category, replacement product, or controlled unavailable page based on business decision. |
| Changed Brand URL | Redirect old brand URL to new brand URL. |
| Removed Download | Redirect to related download category or related product/brand page. |
| Changed Category URL | Redirect old category URL to new category URL. |
| HTTP to HTTPS | Use one preferred secure URL version conceptually. |
| Trailing Slash Variants | Choose one site-wide format and redirect alternatives. |

### Redirect Rules

| Rule | Description |
|---|---|
| Avoid redirect chains | Redirect old URLs directly to final destination. |
| Maintain redirect records | Important URL changes should be tracked. |
| Use relevant destinations | Do not redirect all missing pages to home by default. |
| Review after archiving | Archived products and documents need planned destination behavior. |

## 23. Pagination SEO Considerations

Pagination may be required for product, brand, download, gallery, inquiry, and admin listings.

| Paginated Area | SEO Consideration |
|---|---|
| Product Listings | Category listing pages may require indexability decisions for paginated URLs. |
| Downloads | Document category pagination should avoid duplicate metadata. |
| Gallery | Gallery pagination should maintain category context. |
| Search Results | Search result pagination generally should not be treated as primary SEO content. |
| Admin Listings | Admin pagination should not be indexable. |

### Pagination Rules

| Rule | Description |
|---|---|
| Keep paginated URLs consistent | Use stable parameter or path patterns. |
| Avoid duplicate titles where possible | Paginated pages should have clear context if indexable. |
| Do not expose empty pages | Empty pagination states should not be indexable. |
| Link to next/previous pages clearly | Users and crawlers should be able to navigate listings. |
| Decide canonical behavior | Canonical strategy should be defined for paginated listings before implementation. |
